# 产品、架构与业务测试审查（2026-09-12）

本轮完成代码审查、故障注入回归、业务状态测试和 Release 编译。结论是：安全核心已有较好的防护，但异步状态、页面生命周期和失败反馈的覆盖不足。不能据此宣称所有真机流程已经验收，也不能宣称不存在其他缺陷。

审查基于工作区当前内容，保留了开始前已有的未提交修改。没有安装应用、操作真实用户清理目标、注册特权助手或调用收费云模型。

## 架构规划与落地顺序

保留现有 MacVitalKit 的确定性安全边界；不引入 SwiftUI、不扩展删除白名单、不改变 Helper 信任边界。采用围绕具体缺陷的小步重构，避免一次性重写安全核心。

1. **已落地：隔离区操作起点统一。** `beginOperation` 负责操作标记的事务准备；调用方只在持久化成功后触碰载荷，失败保持可见、可重试。
2. **已落地：绘图样式与窗口控制解耦。** 新建 `AnnotationPalette`；WhiteboardViewModel 不再依赖 ScreenPenController 来取得样式，因此绘图业务可以单独编译测试。
3. **已落地：状态归属调整。** 白板由应用生命周期持有；直播用会话代次隔离回调；扫描结果包含失败信息，UI 不再自行推断“扫描成功”。
4. **下一步：可注入的业务服务。** 将 ScanViewModel、UninstallViewModel、StartupViewModel 对整个 AppEnvironment 的依赖缩小为扫描/清理/索引/进程服务接口。先为每条用户动作补可控异步测试，再迁移；不能只测试状态枚举赋值。
5. **下一步：采集层拆分。** 将 ScreenCaptureKit、AVAssetWriter 和 NWListener 放到适配层，由可注入的会话控制器管理；测试权限拒绝、启动中停止、旧委托、端口失败及写盘失败，无须真正采集用户屏幕。
6. **下一步：持久化与发布验收。** 白板文档、隔离区健康状态、操作历史分别用独立存储类型管理，注入时钟与文件操作失败；随后执行上表的真机矩阵。

优先交付顺序：隔离区恢复能力与后台到期语义 → 异步业务测试与采集会话 → 白板持久化/导出一致性 → 性能与便利功能。每一阶段都应有失败场景验收，不能仅以编译通过作为完成标准。
